### Verified capabilities

- Two official YouTube IFrame players (Deck A / Deck B), Play / Pause / Stop per deck.

- Failure handling: API load failure + retry, player readiness, unavailable embeds

### Decisions and rationale

- **Crossfader position is the single source of truth.** Auto crossfade animates that position,
  so manual and automatic mixing use one code path and the volume meters always match reality.
- **Deck ownership lives on the playlist item**, not on the deck. Reordering is a pure array move.
- **Stop is not “next”.** It reloads the same track from zero (`cuedVideoId` reset) and never
  advances the queue.
- **Natural end never autoplays.** Requirement 7: cue the next item, leave it paused.
- **Titles are best-effort and keyless.** oEmbed works cross-origin; the player’s own metadata is
  a fallback, then a stable `YouTube video <id>`.
- **Playlist import is keyless** (`cuePlaylist` → `getPlaylist`) with a throwaway off-screen
  player; no backend, no API key.
- **Mixes (`RD…`) are detected, not expanded.** YouTube does not expose their track list; the app
  adds the referenced video and keeps an inline explanation instead of pretending.
- **Fades must survive hidden tabs and dead decks** (see issues 3 and 4).
- **Pages base is derived from `GITHUB_REPOSITORY`**, not hardcoded; `VITE_BASE` overrides.

### YouTube IFrame API learnings

- The API **replaces the target `<div>` with an `<iframe>`** (it keeps id/class). Never let Vue
  own that node.
- Embedded players must be at least **200×200**. Hidden probe players go off-screen, not `display:none`.
- `cueVideoById` prepares; `loadVideoById` plays. `stopVideo` may end in any non-playing state, so
  we reset the cue and reload on the next Play.
- `getPlaylist()` works for real playlists (`PL…`) — verified with 14 tracks — and returns **zero
  ids for `RD…` mixes** under every attempt (cue, load, muted autoplay).
- Error codes: `2` invalid params, `5` HTML5 failure, `100` unavailable, `101`/`150` embedding
  disabled, `153` missing referer. All are surfaced per deck with a Release action.
- `setVolume` is per player; a crossfade is just two volume writes driven over time.
- Autoplay needs a user gesture. Muted autoplay did not rescue mix playback in headless.
- Keyless oEmbed (`youtube.com/oembed`) is CORS-enabled and safe in batches (~4 concurrent).
- Watch-page HTML and the RSS feed are **not readable cross-origin**; expanding mixes needs a
  server-side fetch (VPS/serverless) or the user pasting the page HTML.

### Other learnings

- Vue: mutating a raw object that was pushed into a reactive array updates data but does **not**
  trigger rendering. Read the proxy back (`state.items.slice(-n)`).
- Any rAF-driven animation needs a time-based fallback; derive progress from timestamps, not ticks.
- jsdom + a stubbed `window.YT` covers transport/state well; stub `requestAnimationFrame` and
  assert **player volumes**, not just UI state.
- Vitest’s default timeout is 5 s; a test waiting on a 4 s fade needs an explicit per-test timeout.
- CDP debugging: a stale browser can hold the debug port and silently answer for an older profile —
  verify the target URL and use a fresh port/profile.

### Known limitations

- Auto-generated mixes (`list=RD…`, `start_radio=1`) cannot be enumerated; the app adds the
  referenced video and warns. A VPS/serverless endpoint could fix this later.
- Private playlists are unreadable (public/unlisted only).
- Some videos disallow embedding (`101`/`150`); they show an error and a Release button.
- Playback requires a user gesture; background timer throttling can delay a cue by ~1 s (longer
  after several minutes hidden), though fades no longer freeze.
- Icons load from the Font Awesome CDN; text labels remain if it is blocked.
- State is per browser (`localStorage`), restored cued-only; storage sanitizes to 200 items.
- No `LICENSE` file yet (public repo, all rights reserved by default).
